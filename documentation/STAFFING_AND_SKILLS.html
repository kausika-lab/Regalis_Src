02What the system does

Regalis WorkSpace is a coworking-space operations platform for a premium Indian workspace operator. Members book desks, cabins and meeting rooms; staff run the floor, the money and the support desk. Currency is INR and times are handled in IST with UTC storage.

Business purpose

Convert a physical coworking site into a bookable, metered, auditable service: sell time and space (hourly bookings, day passes, monthly passes), collect money (wallet, gateway, invoices), control physical entry (signed QR at the gate), and run back-office operations (housekeeping, inventory, attendance, payroll export, tickets, 16 reports).

User types

Two portals are enforced at login (PortalType.Customer / PortalType.Admin), three user types (Customer, Admin, Staff), and six seeded roles from Persistence/Seed/SeedCatalogue.cs:

RolePortalScope as seeded
CUSTOMERCustomerOwn data only — row-scoped
ADMINAdminAll 103 permissions (wildcard grant)
MANAGERAdminOperations Manager — floor, bookings, calendar
FINANCEAdminMoney and reporting; read-only on operations
SUPPORTAdminTickets, customers, bookings — read-mostly
HOUSEKEEPINGAdminHousekeeping schedules and inventory

Major modules

Derived from the 27 controllers and the permission catalogue: Auth · Bookings (+ Availability, Calendar) · Workspaces (desks, cabins, meeting rooms) · Locations · Passes (day, monthly) · Wallet · Payments · Invoices · Access control (QR gate + logs) · Attendance (+ payroll export) · Housekeeping · Inventory · Services catalogue · Tickets · Notifications · Banners · Reports · Audit · Users / Roles / Menus / Settings · Dashboard · Customers · Profile.

Architecture

Dotted edges are external. Infrastructure reaches Domain only transitively through Application — worth noting because the ASCII art in documentation/ARCHITECTURE.md §2 draws that as a direct arrow, which the .csproj files contradict.

Authentication flow

Ten endpoints on AuthController: login, register, verify-otp, resend-otp, forgot-password, reset-password, change-password, refresh, logout, me. Registration issues a hashed, attempt-capped, single-use OTP. Login returns a short-lived JWT plus a 7-day refresh token; refresh rotates the token and reuse detection revokes the whole token family. Passwords are PBKDF2/HMAC-SHA256 with per-user salt and password history. Lockout is setting-driven. The SPA runs a single-flight refresh on 401 in frontend/src/api/client.ts.

Authorization

Not role-checking — a genuine permission system. 103 codes of the form MODULE.ACTION (BOOKING.CREATE, ACCESS.OVERRIDE, PAYROLL.EXPORT) resolved through a custom PermissionPolicyProvider and HasPermissionAttribute. A fallback policy makes authentication the default, and a reflection test fails the build if any action lacks an explicit attribute. Customer row-scoping returns 404, not 403, for another member's record.

Important business workflows

  1. Booking with paid hold. Created Pending, holding the slot for Booking.PendingHoldMinutes; payment moves it to Confirmed; the BookingHoldSweeper job expires unpaid holds. Confirm runs at serializable isolation with re-checks inside the transaction.
  2. Gate entry. HMAC-SHA256-signed QR verified in constant time; Confirmed → CheckedIn at the gate or in-app; checkout closes to Completed; every transition writes TRN_BookingStatusHistory.
  3. Money. Append-only wallet ledger with compensating entries; gateway signature recomputed server-side; webhooks idempotent on gateway payment id; a client-reported success is never trusted.
  4. Gap-free numbering. NumberSequenceService issues invoice and booking numbers by atomic UPDATE — the one raw-SQL site in the codebase.

11Database testing

SQL level required: intermediate. Comfortable with multi-table joins, aggregates, and reading a schema; no need to author procedures.

Tables to understand

  • MST_User, MST_Role, MST_Permission and the MAP_ junctions — the RBAC core
  • TRN_Booking + TRN_BookingStatusHistory — one row per transition
  • MST_Wallet + TRN_WalletTxn — append-only ledger
  • TRN_Invoice + lines; NumberSequence
  • TRN_AuditLog, access log — insert-only
  • MST_Workspace, MST_Location, MST_WorkspaceType

What to verify

  • CRUD: the UI action produced exactly the expected rows
  • Relationships: no orphans; junctions consistent after role edits
  • Duplicates: unique constraints on email and mobile hold
  • Constraints: negative stock and negative wallet rejected at the database, not just the UI
  • Transactions: a failed confirm leaves no partial rows
  • Consistency: wallet balance equals the sum of its ledger
  • Append-only: no UPDATE or DELETE ever touches audit or ledger rows
  • Backend vs DB: API response matches stored state, especially UTC vs IST

12Automation tester

Automation is strongly recommended — and the tooling decision is already made by the repo, so no invention is needed.

Why these tools

Playwright (1.62.1) is already a dev dependency with 2 specs, a config and a runner script — extend it rather than introduce Cypress. xUnit + WebApplicationFactory already gives 83 API-level integration tests against real SQL Server; new API automation belongs there, not in a separate framework. Vitest is configured for component tests. TypeScript and C# are already required of the team, so no new language is needed.

Risks and skill gaps found

Risk 1 · highest priority

No CI/CD, while the docs assume it. .github/workflows/ is empty and no pipeline config exists anywhere, yet SECURITY.md line 8 states the 101 tests "execute on every merge." The tests are real and runnable via scripts/run-tests.ps1, but nothing enforces them. Every security guarantee in that document rests on a suite no automation runs.

Risk 2

Frontend testing is effectively absent. 7 assertions in a single formatters.test.ts against 33 pages, versus 95 backend tests. The 5 Playwright tests are the only real frontend safety net.

Risk 3

Production secrets in a deployed config file. A live JWT signing key and seed admin password sit in cleartext in the deployed appsettings.Production.json. Anyone holding that key can forge tokens for any user. The source repo is clean; this is a deployment-hygiene failure. Rotate both and move them to the environment.

Risk 4

Two features are stubs, not implementations. MockAccessControlAdapter means physical gate integration is unproven against real hardware. And BookingStatus.NoShow is declared and queried but never assigned anywhere — a no-show is currently unrepresentable, so revenue-recovery and occupancy reporting silently understate it.

Risk 5

Single-process assumptions. Caching is IMemoryCache, the booking sweeper is an in-process hosted service, and booking locks are in-process. Scaling to a second IIS worker or server would break cache coherence and could run the sweeper twice.

Risk 6 · documentation drift

Docs disagree with code in at least three places: ARCHITECTURE.md §2 claims a database/ tree of procedures and views that does not exist and draws a direct Infrastructure→Domain reference the .csproj files contradict; SECURITY.md references a parallel repo and per-merge CI that is absent. A new joiner trusting the docs will be misled — budget onboarding time for reading code over prose.

Lesser gaps: no observability beyond log files; no backup automation in the repo; only 3 EF migrations for 45 entities, so schema history is thin; the Sms channel is enumerated but unimplemented; and QuestPDF's community licence carries revenue conditions worth confirming before go-live.

Direct answers

Is manual testing alone enough? No. A 6-role × 103-permission matrix is 618 combinations, and three of the six recorded security findings were access-control leaks that a matrix sweep catches. Re-running that by hand every release is not credible.

Is automation recommended? Yes, and it is unusually cheap here — Playwright, xUnit and Vitest are already installed and 95 backend tests already pass. The missing piece is a pipeline, not a framework.

What should be automated first? In order: (1) CI running the existing backend suite, (2) the role/permission matrix, (3) the auth lifecycle, (4) the booking→payment→invoice→QR→gate path, (5) money invariants.

Is a dedicated DevOps person required? Not full-time. The stack is a single Windows host with IIS and SQL Server, and the runbook is thorough. Engage someone part-time or shared to fix secret handling, build the pipeline, and establish backups and monitoring — roughly a focused month of work, then low ongoing load. Revisit if you move to multiple servers or the cloud, which the single-process assumptions above would force anyway.
